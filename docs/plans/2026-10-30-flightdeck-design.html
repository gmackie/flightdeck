Flightdeck v1: self-hosted product analytics on Cloudflare Design draft

2026-10-30 · gmackie/flightdeck · brainstorm output, for review before implementation planning

Proposal: Ship one Worker into the user's account. It has an RPC Ingest entrypoint that apps call through service bindings, Durable Objects as the hot layer (a SessionDO builds each journey, an AppDO keeps live counters and transitions), Basin Pipelines → Iceberg on R2 as the raw store of record, and a Kumo + ECharts + React Flow dashboard behind Cloudflare Access. A create-flightdeck CLI provisions everything.

Decisions so far

Storage

Basin Pipelines → Basin Catalog (Iceberg on R2) for raw events and sessions. Durable Objects hold the live state.

Hot layer

One SessionDO per visitor session builds the journey. AppDO shards per app and hour keep live counters and step→step transitions.

UI

@cloudflare/kumo (Base UI + Tailwind v4). ECharts in SVG mode, themed from Kumo tokens. React Flow for journey and funnel builders.

Auth

Cloudflare Access in front of the dashboard; the Worker verifies the Cf-Access-Jwt-Assertion. Ingest has no public HTTP route at all.

v1 scope

Live view + trends, Sankey journeys, funnels, identity + retention.

Architecture

App Workers never talk to storage. They call the FLIGHTDECK binding, and service binding props tell Flightdeck which app is calling. Browser events reach the app's own Worker first, so collection stays first-party and ad blockers don't strip it.

Three data tiers

Hot: Durable Objects

Seconds to about 2 hours

  • Live event stream over hibernating WebSockets
  • Per-hour counters, HLL unique sessions, transition matrix
  • Open sessions, closed by an alarm after 30 minutes idle

Warm: D1

Dashboard history, millisecond reads

  • Control plane: apps, funnels, saved views
  • Hourly and daily rollups: trends, transitions, funnels, retention cohorts
  • Kept small on purpose, well under the D1 size limit

Cold: Iceberg on R2

Store of record, open format

  • events and sessions tables, partitioned by app_id, day(ts)
  • Basin SQL for rollups, backfills, and the Explore page
  • Readable by DuckDB, Spark, and Snowflake, so users can leave with their data

    // ...app logic
  },

3 · Frontend auto-capture

<button data-flightdeck="pricing.cta">Start trial</button>

Inside a Durable Object
import { handleFlightdeck } from "@flightdeckhq/worker";

async fetch(req) {
  const fd = await handleFlightdeck(req, this.env);
  if (fd) return fd; // handled /_fd/e
  // ...DO logic
}

The browser script is under 3 KB. A single delegated listener catches clicks, submits, and opt-in visibility (via IntersectionObserver) for any [data-flightdeck] element. It batches events and flushes them with sendBeacon when the page is hidden. Extra properties go in data-flightdeck-* attributes. Session IDs live in sessionStorage; a privacy option turns off the persistent anonymous ID.

Event flow

  1. Capture

    The browser batches events, or server code calls track(). withFlightdeck adds request context such as request.cf country, parsed user agent, and referrer. It never forwards the raw IP.

  2. Ingest (RPC)

    Reads ctx.props.appId and rejects unknown apps. Validates batches against a shared schema (size caps, at most 50 events, property limits), stamps event_id and received_at, and normalizes routes (/users/123 → /users/:id).

  3. Fan out

    Sends raw events to the events Pipelines stream, which delivers exactly once to Iceberg, and in parallel appends them to SessionDO(app:session).

  4. Journey assembly

    The SessionDO orders steps and collapses repeats. It sends each new prev → next transition to AppDO(app:hour) right away, so the live Sankey updates. identify() attaches user_id to the rest of the session.

  5. Session close

    After 30 minutes idle, an alarm writes one compact path record (steps, entry, exit, duration, user) to the sessions stream, then the DO clears its storage.

  6. Rollup

    A cron job runs Basin SQL over closed hours to compute trends, transitions, funnel conversion, and weekly retention cohorts keyed by coalesce(user_id, anonymous_id), and upserts the results into D1.

Journey view direction

Illustrative only: invented data, rendered with ECharts in SVG mode using theme tokens. This shows the intended look, not real numbers. Real journeys keep the top N steps at each depth and group the rest as "other" so the chart stays readable.

Onboarding and deployment

Install

npx create-flightdeck uses wrangler auth or an API token. It creates the R2 bucket, enables Basin Catalog, creates the events and sessions streams, sinks, and pipeline SQL, creates D1 and runs migrations, deploys the Worker, and creates the Access application. It's idempotent, and flightdeck doctor re-checks everything.

Add an app

Dashboard → New app creates an appId and shows the wrangler snippet and install commands, plus a "waiting for first event" check that lights up over the live WebSocket.

Requirements

Workers Paid plan, because Basin Pipelines requires it. Zero Trust free tier for Access (up to 50 users). No external services.

Later

A Deploy to Cloudflare button, if it can provision Pipelines (to be checked), and a Terraform module built on the cloudflare_pipeline_* resources.

Scope

v1 goals

  • RPC ingest through service bindings, with typed SDK
  • data-flightdeck auto-capture through a first-party endpoint on Workers and DOs
  • Live stream + trends, Sankey journeys, funnels (React Flow builder), identity + retention
  • One-command install in the user's own account, behind Access
  • Raw data in open Iceberg tables the user owns

Non-goals for v1

  • Public HTTP ingest for apps that aren't on Workers
  • Session replay and heatmaps
  • Multi-tenant SaaS hosting
  • Feature flags and experiments
  • Its own login system (Access only)

Mitigations
RiskMitigation
R1 · One AppDO per app and hour becomes a write hotspot for high-traffic appsSessionDOs combine writes into batches; AppDO keys become app:hour:shard(n) with fan-in reads; n is set per app.
R2 · Pipelines needs Workers Paid plus an R2 catalog token, and Access needs Zero Trust onboardingThe CLI checks the plan up front, walks the user through creating the token, and saves progress so a rerun resumes where it stopped; doctor explains each failure.
R3 · Path cardinality makes the Sankey unreadableRoute normalization, top N per depth with an "other" group, a depth limit, and anchoring on a start or end step.
R4 · Basin SQL is too slow for interactive dashboardsThe dashboard reads from DOs and D1 rollups; Basin SQL serves only rollups and Explore, with async query status.
R5 · One DO per session raises request costsBrowser batching (one RPC per flush), SessionDO alarms instead of polling, storage cleared on close.
R6 · Any Worker in the account could claim another app's appId in propsAcceptable, since service bindings only work within one account. An optional per-app key in props, checked against a hash in D1, closes the gap.

Resolved decisions

npm scope

Packages publish under @flightdeckhq (/worker, /browser, /schema); the CLI stays unscoped as create-flightdeck.

Session timeout

30 minutes idle.

Anonymous ID

On by default: a persistent localStorage ID, which a privacy option can turn off.

Access identity

When a request carries Cf-Access-Jwt-Assertion, withFlightdeck forwards it over RPC. Ingest verifies it against the team JWKS and sets user_id to the Access sub, the same as calling identify().
